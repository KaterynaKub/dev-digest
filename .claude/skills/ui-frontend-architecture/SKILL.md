# UI-архітектура фронтенду

Правила **розміщення** коду та **меж** між модулями у React/Next.js застосунках.

Одне правило, з якого випливає решта:

> **Залежності спрямовані всередину. Фіча не знає про свій маршрут, дизайн-система не знає про домен.**

Це фронтенд-аналог того, що `onion-architecture` робить для backend'а DevDigest:
там шари йдуть від домену назовні, тут — від маршруту всередину до примітивів.

## Коли застосовувати

Завантажуйте цей скіл, коли ви:

- створюєте нову теку фічі або вирішуєте, куди покласти файл
- рев'юєте імпорти між фічами чи шарами
- проєктуєте шар доступу до даних (DAL) і Server Actions
- вирішуєте, де поставити `use client`
- обираєте, де має жити конкретний шматок стану
- рефакторите фронтенд, що розростається

## Рівні важливості

- **CRITICAL** — порушення створює циклічні залежності, витік секретів або блокує рефакторинг
- **HIGH** — призводить до ерозії структури в міру зростання кодової бази
- **MEDIUM** — шкодить читабельності та швидкості онбордингу

## Базова структура (CRITICAL)

```
src/
├── app/                    # ЛИШЕ маршрутизація
│   └── (dashboard)/
│       ├── layout.tsx
│       ├── page.tsx
│       └── _components/    # тільки для цього маршруту
├── features/               # бізнес-домени
│   └── billing/
│       ├── api/            # виклики DAL, Server Actions
│       ├── components/     # UI домену
│       ├── model/          # типи, схеми, стан домену
│       └── index.ts        # публічний API фічі
├── components/ui/          # дизайн-система, без домену
└── lib/                    # DAL, server-only, утиліти
```

Правила:

- `app/` містить **лише** `page`/`layout`/`loading`/`error`/`route` і тонкі композиції. Жодної
  бізнес-логіки — сторінка збирає фічу з `features/`, а не реалізує її.
- Вкладати теки в `app/` тільки тоді, коли цього вимагає URL. Для організації — route groups.
- Компонент, специфічний для одного маршруту, живе в `_components/` поруч, а не в глобальному
  `components/`.
- Кожна фіча має `index.ts` як єдину точку входу.

## Напрямок залежностей (CRITICAL)

Залежності односпрямовані. Це те правило, порушення якого найдорожче виправляти пізніше.

```
app/  →  features/  →  lib/, components/ui/
```

- `app/` імпортує з `features/` — не навпаки. Фіча ніколи не знає про свій маршрут.
- `features/` імпортує з `lib/` і `components/ui/` — не навпаки. `lib/` не знає про домени.
- `components/ui/` не імпортує **нічого** доменного — це дизайн-система, придатна для будь-якого
  застосунку.
- **Фіча не імпортує з іншої фічі напряму.** Якщо `billing` потребує щось із `users` — імпорт
  іде через публічний `features/users/index.ts`, ніколи не через `features/users/model/internal.ts`.
- Циклічний імпорт між фічами — сигнал, що межу проведено неправильно. Спільне піднімається
  в `lib/` або виділяється в третю фічу.

Перевіряти автоматично: `eslint-plugin-boundaries` або `import/no-restricted-paths`.

## Публічний API фічі (HIGH)

Кожна фіча експортує тільки те, що є її контрактом:

```ts
// features/billing/index.ts
export { InvoiceList } from './components/invoice-list';
export { createInvoice } from './api/create-invoice';
export type { Invoice } from './model/types';
// внутрішні хелпери, схеми, приватні компоненти НЕ експортуються
```

- Усе, чого немає в `index.ts`, є деталлю реалізації і може змінюватися вільно.
- Імпорт із глибини чужої фічі (`features/billing/model/mapper`) — порушення межі.
- Якщо `index.ts` розростається до десятків експортів — фіча робить забагато, час ділити.

## Шар доступу до даних (CRITICAL)

Уся робота з даними централізована в DAL, а не розсипана по компонентах і діях.

- Кожен модуль DAL починається з `import 'server-only'` — межа тримається на етапі збірки,
  а не на дисципліні.
- **Перевірки автентифікації та прав живуть усередині функцій DAL**, а не в місцях виклику.
  Server Action — це публічна HTTP-точка: відсутність перевірки в ній є вразливістю, а не
  недоглядом.
- DAL повертає плаский DTO, ніколи не сирий об'єкт ORM. Значення, що повертається з Server
  Action, серіалізується прямо клієнту — сирий об'єкт витікає внутрішніми колонками.
- Server Action лишається **тонкою обгорткою**: виклик DAL плюс `revalidatePath`/`revalidateTag`.
  Логіка в дію не переїжджає.
- Серверний компонент викликає функції DAL напряму — не ходить `fetch`-ом на власний
  `localhost`/Route Handler.

Деталі вибору між Server Component, Server Action і Route Handler — у `next-best-practices`
→ `data-patterns.md`.

## Межа `use client` як архітектурне рішення (CRITICAL)

Директива визначає, який код поїде в браузер, тому це рішення про структуру, а не про синтаксис.

- Ставити `use client` **якомога нижче** по дереву — на листках, а не на гілках.
- Директива «заразна»: усе, що імпортує клієнтський файл, теж стає клієнтським. Утиліта,
  імпортована одним клієнтським компонентом, їде в бандл цілком.
- **Ніколи не в кореневому `layout.tsx`** — весь застосунок під ним успадковує межу.
- Провайдери контексту виносити в окремий клієнтський файл (`providers.tsx`), а layout лишати
  серверним.
- Серверний компонент передається в клієнтський через `children`, а не імпортом — це єдиний
  спосіб лишити піддерево на сервері.
- Монолітний клієнтський компонент розділяти: статична «оправа» лишається на сервері,
  клієнтською стає лише інтерактивна частина.

Технічні обмеження межі (серіалізовність, async) — у `next-best-practices` → `rsc-boundaries.md`.

## Розміщення стану (HIGH)

Серверний і клієнтський стан — різні задачі, і змішувати їх в одному сховищі не варто.

| Тип стану | Де живе |
| --- | --- |
| Дані з сервера (списки, деталі, пагінація) | Кеш запитів (TanStack Query) або RSC |
| Стан UI, спільний для піддерева | Локальний `useState` у найближчому спільному предку |
| Глобальний клієнтський стан | Легкий стор (Zustand), імпортується з `features/*/model` |
| Фільтри, пошук, пагінація, вкладки | URL search params |
| Конфігурація, тема, поточний користувач | Context як dependency injection |

- Серверні дані **не дублюються** в глобальний стор — джерело істини одне.
- Стан, що відновлюється з URL, у сторі не тримається: посилання має відтворювати екран.
- Context — це ін'єкція залежностей, а не сховище стану застосунку.
- Стор домену належить фічі (`features/billing/model/store.ts`), а не глобальній теці.

Правила самих хуків і `useState` — у `react-best-practices`.

## Композиція маршрутів (MEDIUM)

- Route groups `(name)` — для організації за доменом чи командою та кількох кореневих layout'ів
  без впливу на URL.
- Приватні теки `_name` — для колокації того, що не є маршрутом.
- Сторінка в `app/` має читатися як опис: отримати параметри → викликати фічу → віддати розмітку.
  Якщо `page.tsx` перевищує ~50 рядків, логіка просочилася з `features/`.
- Спільний layout не використовувати як місце для логіки — він рендериться для всього піддерева.

## Дизайн-система (MEDIUM)

- `components/ui/` містить примітиви без знання про домен: `Button`, `Input`, `Card`, `Dialog`.
- Примітив не приймає доменні типи. Не `<UserCard user={User} />`, а `<Card>` із композицією.
- Доменний компонент (`InvoiceRow`) належить фічі, навіть якщо виглядає узагальнено.
- Дублювання примітиву в кількох фічах — сигнал підняти його в `components/ui/`.
  Але піднімати після **третього** повторення, не після першого.

## Проти передчасної абстракції (HIGH)

- Колокація перемагає узагальнення: компонент, хук, типи й тести однієї фічі лежать разом.
- Абстракція з одним споживачем — передчасна. Спершу дублювання, потім виділення.
- Не створювати теку `features/`, поки фіча одна. Структура росте за потребою, а не наперед.
- Шар, що лише передає виклик далі, прибирати — кожен рівень непрямування має заробляти
  своє існування.

## Ознаки ерозії архітектури

Симптоми, за якими видно, що межі поплили:

- Імпорти вигляду `../../../features/other/model/internal`
- `use client` у файлі, який не має жодного обробника подій чи хука
- Бізнес-логіка всередині `app/**/page.tsx`
- Одні й ті самі серверні дані і в кеші запитів, і в глобальному сторі
- `components/` із сотнею файлів без групування
- Server Action, що звертається до БД напряму, минаючи DAL
- Фіча, яка імпортує три інші фічі — ймовірно, це не фіча, а сторінка
